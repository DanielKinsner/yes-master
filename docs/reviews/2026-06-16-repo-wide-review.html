The "so what" — in plain English

YES Master is in good shape structurally and is unusually well-documented; most of what the audit found is narrow correctness and missing safety nets around the non-negotiables, not rot. But there are a handful of real teeth. Here is what actually matters:

  1. 1. One genuine crasher, on Android. A multi-channel import (or a phone that opens the audio output at fewer channels than the source) makes the Android audio engine write past the end of its buffer on the real-time audio thread — memory corruption, i.e. a crash or worse. It's the only critical. The good news: it's already on the roadmap as S4.3, just not built yet.
  2. 2. Album Master's headline feature is silently switched off. The album "loudness arc" (the thing that makes tracks rise and fall across an album) is computed and then thrown away on the default delivery profile — every track lands at flat −14 LUFS. Tone still moves; loudness doesn't. Nobody's tracking this. (High.)
  3. 3. Saving a preset can wipe all your presets. If the presets file ever fails to parse (e.g. after a routine settings-schema change), the next "save preset" silently overwrites the file with just the one new preset — every earlier preset gone, no error. Real, untracked data loss. (High.)
  4. 4. The export "this master is corrupt" safety check can never actually fire. The spec promises a post-render critical when a render goes non-finite (NaN/Inf). But the only value it checks is laundered to a finite number first, and nothing scans the actual samples — so a corrupt master would be written and reported as a clean ~−70 LUFS file. (High potential; needs the DSP to misbehave to trigger.)
  5. 4b. rev 2 Desktop "Export LUFS" preview can lie on 48/96k sources. The live preview computes its landing level on the un-resampled source, while the actual export resamples to 44.1k (Standard) first and lands there — so what you hear in preview isn't what lands in the file, for any source whose rate ≠ the export rate. The iPhone app was already fixed for exactly this; desktop wasn't. Codex flagged this as priority #1; it directly dents the "audition at the same level" promise. (Medium — the exported file is correct; only the preview drifts.)
  6. 5. Three of your sacred non-negotiables rest on a single un-tested line each. "Volume Match never changes export level" (album path), "Original/Mastered preserves the playhead," and "never overwrite a source/render" are each one careless edit from breaking, with no pinning test to catch it. These are cheap, additive tripwires — the highest safety-per-effort work in the report.

Everything else is medium correctness polish (stale meters on track-switch, an off-grid Standard loudness leak, a private-path gap in .gitignore) and a long tail of safe cleanup (dead code, duplicated helpers, CSS band-aids). The plan at the end sequences all of it.

How "Fix now" vs "Hold" was decided

Derived from the project's own non-negotiables (CLAUDE.md): bugs and additive guardrails = Fix now; structural refactors of working, stability-critical paths (DSP chain, export writer, the audio hot loop) = Hold til post-ship — because Track Master stabilization comes before re-shaping working spec-critical code. Pure-cosmetic and dead-code cleanup is its own low-risk backlog. Each card also carries a tracked / untracked tag mapping it to the 2026-06-12-shippability-roadmap.md slice that already owns it (or noting it's new).

Subsystems read: Rust backend (~24 files incl. dsp.rs 5.2k lines, audio.rs 3.9k), React/TS frontend (~60 files incl. useTrackMaster.ts 2.3k), iPhone (Swift + Rust bridge), Android (Kotlin + Rust bridge), the bindings.ts wire contract, and all of docs/.

critical ✓ verified 3/3 fix now D1+D3 · Android audio tracked · S4.3 (AN-02)

Android audio callback writes out-of-bounds for multi-channel sources (memory corruption on the RT thread)

apps/android-native/rust/src/aaudio.rs:98-110, 137-164

What: open() only requests the channel count via AAudioStreamBuilder_setChannelCount and never reads back AAudioStream_getChannelCount. The data callback then sizes its output slice from the source channel count: from_raw_parts_mut(audio_data, frames * pump.channels()). AAudio's request is advisory; when the OS opens fewer channels (a 6-channel import on a 2-channel phone, or a stereo source routed to a mono device), pump.fill writes frames×6 floats into a frames×2 buffer. The live decode path applies no fold-down (that only happens in album/render delivery), so a 5.1 file reaches here at 6 channels.

Why it matters: An out-of-bounds heap write on the real-time audio callback thread, reachable by a normal user importing a multichannel file — undefined behavior, crash, or silent corruption. The iPhone path is guarded (its render block bounds each channel); Android has no equivalent. This is the only critical.

Fix: After openStream, query the actual channel count / sample rate / format; size the callback slice from the actual count and either down/up-mix or refuse to start on mismatch. (Exactly what roadmap slice S4.3 already specifies.)

Album loudness arc is silently discarded under the default delivery profile — every track lands flat

src-tauri/src/album_render.rs:263-264 · types.rs:617-621

What: apply_album_shadow writes the arc-modulated target into advanced.lufs_offset_db. Fix: In the album shadow, force a Custom-equivalent landing so effective_target_lufs() returns the arc-modulated value (mirror the existing adaptive-field stripping at album_render.rs:294-296), or land against an explicit absolute target. high ✓ verified 3/3 fix now D1 · Persistence untracked · new

Saving/deleting a user preset wipes ALL presets when the file fails to parse

src-tauri/src/settings.rs:31, 40, 59, 66, 83

What: save_user_preset does read_presets(&path).unwrap_or_default() then pushes + writes. But read_presets returns Err on any JSON parse failure (only a missing file yields empty). UserPreset embeds MasteringSettings, which has required non-#[serde(default)] fields — so one preset written under an older/newer schema makes the entire vector fail to parse. unwrap_or_default() swallows that into an empty vec and the next save atomically overwrites the file with only the new preset.

Why it matters: Silent, permanent user-data loss triggered by routine schema evolution — no error shown. This is not covered by roadmap S1.5 (which lists audio.rs/files.rs/project.rs, not the presets path).

Fix: On parse error, do not fall back to default-and-overwrite — surface the error (refuse to save, tell the user the file is unreadable) or back up the unparseable file before writing.

high likelihood: med ✓ verified 2/3 fix now D1 · Export integrity rev 2 · S1.1 cause shipped; detection gap remains

Non-finite (NaN/Inf) render samples are written to the master, and the spec's post-render "corrupt render" critical can never fire

src-tauri/src/engine.rs:861-963 · analysis.rs:265-271 · exports.rs:135 · wav_writer.rs:248

What: The only post-chain integrity signal is sanitize_lufs(ebu.loudness_global()), and sanitize_lufs maps any non-finite reading to a finite −70.0. Samples then go straight to write_wav with no NaN/Inf scan; the writer passes NaN through (f32::NAN.clamp(-1,1) is still NaN; int casts NaN→0 = silent dropouts). So measured_lufs is always finite and the if !report.measured_lufs.is_finite() critical in exports.rs:135 can never trip.

Why it matters: If the chain ever emits NaN/Inf (divide-by-zero, denormal blowup, coefficient instability), the app writes a corrupt / silently-zeroed master and reports a clean ~−70 LUFS. Skeptics rated likelihood medium (needs the DSP to actually misbehave) and the consequence is "ships a broken master that looks fine." rev 2 The most likely low-rate cause — Nyquist instability — is already closed by the shipped nyquist_safe_freq_hz clamp (S1.1, dsp.rs:55-64), which lowers the trigger probability further. But the detection gap is independent and remains: nothing scans the rendered samples, so any future NaN source still ships silently.

Fix: Add a finite-sample scan (samples.iter().all(|s| s.is_finite())) before write_wav and raise a post-render Critical on failure — or stop sanitizing the measured LUFS that feeds the receipt so the existing critical can fire.

Desktop live Preview-LUFS landing is measured at the source rate, not the render rate — WYSIWYG drift on 48/96k sources

src-tauri/src/audio.rs:1059-1094 (no resample) vs engine.rs:461-477 (render_preview_landing_window resamples) · export lands at render rate: engine.rs:832-840, 890-903 · iPhone uses the shared path: live_stream.rs:727

What: The desktop preview worker export_landing_gain_lin_for_preview builds its chain and measures integrated LUFS + true-peak at the source sample_rate and never resamples.
