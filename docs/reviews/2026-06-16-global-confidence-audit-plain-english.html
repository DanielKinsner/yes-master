YES Master Global Confidence Audit

Plain-English readout from the repo-wide confidence and archaeology audit on 2026-06-16.

Bottom Line

YES Master does not look like a repo where the whole product is secretly off the rails. Track Master, export safety, album format rendering, mobile bridge parity, and private-audio hygiene all have real evidence behind them.

The risk is more specific: a handful of important promises are split across code, docs, and tests. The largest issue is that Album Master can export from live UI choices that are not saved into project files. The second big one is that desktop live Preview LUFS is not using the same rendered-rate measurement path that export and iPhone live preview use.

Confidence Medium-high for Track Master core. Medium for Album/project persistence. Medium-low for docs navigation.
Biggest Risk Saved Album projects can reopen with different Album-panel choices than the user expects.
Most Confusing Area Current-looking docs that are actually historical or partially stale.

The Short List

P1

Album projects do not save all Album-panel choices

The app saves the tracks, per-track settings, album intent, and override flags. It does not save the live Album-panel values for arc, title, intensity, sample rate, or bit depth. Those same values are used when exporting an album.

Plain English: a user can set up an album, save it, reopen it later, and accidentally export with default or Auto choices instead of the choices they made.

P1

Desktop live Preview LUFS can disagree with export

The offline renderer and the shared preview helper measure loudness after sample-rate conversion. Desktop live audition has its own path that measures at the source sample rate. iPhone live preview already uses the shared helper.

Plain English: for 48 kHz or 96 kHz sources, the thing you hear live on desktop may not land exactly like the file the app exports.

P2

Partial analysis failures can be invisible

If a batch has several tracks and one fails analysis, the backend returns the successful tracks and logs the failure to stderr. The frontend does not clearly detect that one requested track is missing from the results.

Plain English: one bad or moved file can leave a track sitting in the app without analysis while the overall operation still looks successful.

P2

Android native ARM64 checks are not in CI

The local docs require an Android Rust host test and an ARM64 cargo ndk check. CI runs Android JVM tests and host bridge tests, but not the actual ARM64 native check.

Plain English: a pull request can go green while a real Android native build/link issue is still hiding.

P2

Album fold-down happens, but the UI does not say it happened

The backend correctly folds above-stereo sources down to stereo and records it in report data. The Album receipt only shows upmix advisories, not fold-down advisories.

Plain English: the app does the right audio conversion but does not tell the user about one important kind of conversion.

Docs That Need Care

Several docs still look current but describe older states. These are not all product bugs, but they are dangerous for future agents.

  • README.md still says Standard styles are Balanced, Bright, Warm, Heavy. The app now shows Universal, Clarity, Tape, Oomph.
  • APP_BEHAVIOR.md still says the private fixture matrix needs a longer run. Release evidence says the run completed; listening signoff remains.
  • ANDROID_NATIVE_SPEC.md still describes A4 as ongoing and says there is no process-death restore. Wave 9 says that catch-up shipped.
  • docs/IPHONE_APP.md points to an iPhone handoff that says it is historical and also contains stale "authoritative" control names.
  • ADAPTIVE_DSP_NEXT_STEPS.md still sounds like Tier-1 guardrails are not accepted, while current release docs say owner listening accepted them on 2026-06-11.

Cleanup Debt

The largest cleanup hotspot is src/App.css. It still contains old selector families that no production TypeScript/TSX files appear to use. That makes future UI work harder because old CSS can look intentional.

  • Examples: .empty-state-glyph, .analysis-summary-icon, .quality-summary-*, .workspace-section-label, .advanced-panel-slot, and .advanced-slot-body.
  • The roadmap already described a CSS selector inventory test. That idea is still useful, but the old class counts are stale and should be regenerated.
  • Rust comments near Album rendering still describe the pre-Wave-9 world where mixed sample rates or channels failed. The code and tests now do better than the comments say.

Things That Looked Scary But Checked Out

Export overwrite protection: normal render paths reject source overwrite and uniquify prior renders. I did not find a material current-flow overwrite bug.

Album mixed-rate/mixed-channel backend: this is shipped and tested. The issues are UI receipt copy and stale comments, not backend render behavior.

Original/Mastered switching: the playhead preservation path is wired through the current transport time.

Private audio: private fixtures and generated renders are ignored. The tracked test-output exception appears intentional.

What I Would Do Next

Fix the two P1s first: Album project persistence, then desktop live Preview LUFS rendered-rate parity. After that, fix partial analysis feedback and Android native verification. Docs cleanup can happen in a separate, low-risk pass.

The current state is workable, but the repo needs a little truth consolidation. The code has done a lot of the hard work; now the saved-project contract, live-preview parity, and docs need to catch up.
